# 🛡️ Kubernetes SecurityContext

## 🧭 Overview

The **SecurityContext** in Kubernetes defines *how a Pod or container runs at the OS level*.  
It controls permissions, privileges, file ownership, and kernel-level capabilities.

Think of it as **“sandbox settings”** for each Pod or container — ensuring workloads don’t break isolation or escalate privileges.

---

## 🧩 Levels of SecurityContext

| Level | Description | Example |
|--------|--------------|----------|
| **Pod-level (`.spec.securityContext`)** | Applies defaults to all containers in the Pod | `runAsUser: 1000` |
| **Container-level (`.containers[].securityContext`)** | Overrides Pod-level settings for specific containers | `allowPrivilegeEscalation: false` |

---

## ⚙️ Common SecurityContext Fields

| Field | Description | Example | Recommended For |
|--------|--------------|----------|------------------|
| `runAsUser` | Runs container as a specific user ID (UID) | `runAsUser: 1000` | Avoid running as root |
| `runAsGroup` | Sets the primary group ID | `runAsGroup: 3000` | Match app’s internal permissions |
| `runAsNonRoot` | Ensures Pod doesn’t run as UID 0 | `runAsNonRoot: true` | Mandatory in restricted profiles |
| `fsGroup` | Changes ownership of mounted volumes | `fsGroup: 2000` | Shared storage permissions |
| `readOnlyRootFilesystem` | Prevents writing to the container’s root FS | `readOnlyRootFilesystem: true` | Immutable workloads |
| `allowPrivilegeEscalation` | Prevents `setuid` or similar privilege jumps | `allowPrivilegeEscalation: false` | Hardened security |
| `privileged` | Gives full root capabilities on host | `privileged: true` | Only for system daemons |
| `capabilities` | Add/drop specific Linux kernel capabilities | `drop: ["ALL"]` | Fine-grained privilege control |
| `seccompProfile` | Limits syscalls using Linux seccomp | `type: RuntimeDefault` | Sandbox defense |

---

## 🧱 Example 1 — Secure Application Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-nginx
  labels:
    app: web
spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 1000
    fsGroup: 2000
  containers:
    - name: nginx
      image: nginx:latest
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
        seccompProfile:
          type: RuntimeDefault
```
✅ Explanation:
- Pod runs as user/group 1000 (non-root)
- No privilege escalation
- No write access to root filesystem
- All Linux capabilities dropped
- Seccomp restricts risky syscalls

## 🧩 Example 2 — Pod-Level vs Container-Level Override
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mixed-security
spec:
  securityContext:
    runAsUser: 2000
  containers:
  - name: app
    image: busybox
    command: ["sh", "-c", "id && sleep 3600"]
  - name: root-container
    image: busybox
    securityContext:
      runAsUser: 0
      allowPrivilegeEscalation: true
```
🧠 Result:
- app runs as UID 2000
- root-container explicitly overrides and runs as root (container settings overrides pod level settings)

## 🔒 Security Hardening in Practice
| Goal                         | Setting                               |
| ---------------------------- | ------------------------------------- |
| Prevent privilege escalation | `allowPrivilegeEscalation: false`     |
| Drop all kernel capabilities | `capabilities.drop: ["ALL"]`          |
| Enforce non-root execution   | `runAsNonRoot: true`                  |
| Make root FS read-only       | `readOnlyRootFilesystem: true`        |
| Limit system calls           | `seccompProfile.type: RuntimeDefault` |

## 💬 Summary
| Feature                    | Purpose                             | Example          |
| -------------------------- | ----------------------------------- | ---------------- |
| `runAsUser`                | Avoid root execution                | `1000`           |
| `allowPrivilegeEscalation` | Prevent `sudo` or `setuid` binaries | `false`          |
| `readOnlyRootFilesystem`   | Immutable container FS              | `true`           |
| `capabilities`             | Fine-grained kernel privileges      | `drop: ["ALL"]`  |
| `seccompProfile`           | Syscall sandbox                     | `RuntimeDefault` |
| `fsGroup`                  | Volume access control               | `2000`           |

**🧩 Pro Tip: Always define securityContext at both Pod and container levels — Pod-level for consistency, and container-level for exceptions (like init containers or sidecars).**



# 🔐 Kubernetes Pod Security Standards (PSS)

## 🧭 Overview

Kubernetes **Pod Security Standards (PSS)** define a set of **security profiles** that govern **what a Pod is allowed to do**.  
They help cluster administrators enforce best practices without manually inspecting every YAML manifest.

PSS replaced the deprecated **PodSecurityPolicy (PSP)** feature in Kubernetes 1.25+.

---

## 🎯 Goal

To prevent containers from:
- Running as root unnecessarily
- Accessing host resources (like `/proc` or network interfaces)
- Escaping containers
- Using dangerous capabilities

---

## 🧩 3 Levels of Pod Security

| Level | Description | Typical Use Case |
|--------|--------------|------------------|
| **Privileged** | Most permissive — allows full host access. | For system-level workloads (CNI, CSI, monitoring agents). |
| **Baseline** | Prevents known privilege escalations but is lenient for common apps. | For standard workloads that don’t need root-level access. |
| **Restricted** | Most secure — follows Kubernetes and NSA hardening guides. | For sensitive workloads in production or multi-tenant clusters. |

---

## 🧠 Level-wise Explanation

### 🥇 1. Privileged

- No restrictions.
- Allows host networking, PID/IPC sharing, privilege escalation, etc.

✅ Use Case:  
CNI plugins (like Calico), CSI drivers, node-level daemons.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: privileged-pod
  labels:
    pod-security.kubernetes.io/enforce: privileged
spec:
  hostNetwork: true
  containers:
  - name: debug
    image: nicolaka/netshoot
    securityContext:
      privileged: true
```


## 🥈 2. Baseline
Blocks known privilege escalations.
Prevents:
  - Privileged containers
  - HostPath volume mounts (except safe paths)
  - Host networking/PID/IPC
  - Dangerous Linux capabilities

✅ Use Case:
Most application workloads in dev/stage.
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: baseline-pod
  labels:
    pod-security.kubernetes.io/enforce: baseline
spec:
  containers:
  - name: app
    image: nginx
    securityContext:
      allowPrivilegeEscalation: false
      runAsNonRoot: true
```

🥉 3. Restricted
Enforces least privilege and strong isolation.
Prevents:
  - Running as root
  - Privilege escalation
  - Host namespaces
  - Unsafe volume types

✅ Use Case:
Production environments, financial/government workloads.
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: restricted-pod
  labels:
    pod-security.kubernetes.io/enforce: restricted
spec:
  containers:
  - name: app
    image: nginx
    securityContext:
      runAsNonRoot: true
      allowPrivilegeEscalation: false
      seccompProfile:
        type: RuntimeDefault
      capabilities:
        drop: ["ALL"]
```

🧱 Namespace-Level Enforcement
PSS is applied via namespace labels, not at Pod level directly.
🔖 Example:
```bash
kubectl label namespace dev \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/audit=baseline \
  pod-security.kubernetes.io/warn=privileged
```

## 🔍 Behavior:
| Label     | Purpose                            |
| --------- | ---------------------------------- |
| `enforce` | Blocks Pods violating that profile |
| `audit`   | Logs violations but allows         |
| `warn`    | Prints warnings at admission time  |

🧩 Behind the Scenes
When you apply PSS:
- Kubernetes Admission Controller checks Pod specs against the enforced standard.
- If violation found → reject or warn depending on label.
- This happens before Pod creation (admission stage).

**🧩 Pro tip: Always start with baseline in dev, and restricted in prod — unless a workload needs elevated privileges (like CNI or CSI plugins).**



# 🌐 Kubernetes Network Policies — Deep Dive

## 🧭 Overview

By default, **all Pods in a Kubernetes cluster can talk to each other freely** — across namespaces, IPs, and ports.  
That’s risky in production.

A **NetworkPolicy** is a Kubernetes resource that acts like a firewall for Pods.  
It defines **which Pods can communicate (ingress/egress)** and **on which ports**.

---

## 🧩 Key Concept
- Network Policies apply to **Pods**, not Nodes.
- Policies are **additive** → multiple policies can apply to a Pod.
- Policies only take effect if your CNI (Container Network Interface) plugin supports them (e.g., Calico, Cilium, Weave Net).

---

## 🧱 Supported CNIs for NetworkPolicy
| CNI Plugin | Supports NetworkPolicy |
|-------------|-------------------------|
| Calico | ✅ Full support |
| Cilium | ✅ Full support |
| Weave Net | ✅ Partial |
| Flannel | ❌ Not supported |
| Amazon VPC CNI (EKS default) | ⚠️ Limited — use Calico add-on for full enforcement |

---

## ⚙️ Anatomy of a NetworkPolicy

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
  namespace: prod
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080
```
| Section        | Meaning                                                   |
| -------------- | --------------------------------------------------------- |
| `podSelector`  | Selects target Pods (the ones being protected)            |
| `policyTypes`  | Type of traffic controlled (`Ingress`, `Egress`, or both) |
| `ingress.from` | Who can send traffic to selected Pods                     |
| `ports`        | Allowed ports/protocols                                   |

### 📘 This policy says:
**Only Pods labeled app=frontend can access Pods labeled app=backend on TCP port 8080.**

## Egress Policy
Controls outgoing traffic from a Pod.
Example:
```yaml
policyTypes:
  - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              env: prod
        - ipBlock:
            cidr: 10.0.0.0/16
      ports:
        - protocol: TCP
          port: 443
```
This allows egress to:
- Pods in namespaces labeled env=prod
- IPs in 10.0.0.0/16 on port 443 (HTTPS)

## 🧠 Network policies have 3 fields -> Pod, Namespace & IP Selectors
| Selector            | Used For                           | Example                        |
| ------------------- | ---------------------------------- | ------------------------------ |
| `podSelector`       | Filter Pods within same namespace  | `matchLabels: {app: frontend}` |
| `namespaceSelector` | Select Pods in specific namespaces | `matchLabels: {team: devops}`  |
| `ipBlock`           | Whitelist/blacklist CIDR ranges    | `cidr: 10.0.0.0/16`            |


## 💡 Example — Deny All Traffic
The most restrictive policy.
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
spec:
  podSelector: {}
  policyTypes:
    - Ingress
```
🧠 Meaning:
Selects all Pods in the namespace and blocks all inbound traffic.

## 🔐 Example — Allow Only DNS and Internal Traffic
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: internal-allow-dns
  namespace: prod
spec:
  podSelector: {}
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector: {}
          podSelector:
            matchLabels:
              app: dns
      ports:
        - protocol: UDP
          port: 53
```
✅ Allows egress only to the in-cluster DNS Pod on UDP 53.


## ☁️ AWS EKS Example
EKS uses Amazon VPC CNI, which doesn’t fully enforce NetworkPolicies.
To enable full functionality:
```bash
kubectl apply -f https://docs.projectcalico.org/manifests/calico.yaml
```
Then apply a policy:
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: eks-web-access
  namespace: web
spec:
  podSelector:
    matchLabels:
      app: nginx
  ingress:
    - from:
        - ipBlock:
            cidr: 10.0.0.0/16
      ports:
        - protocol: TCP
          port: 80
```
✅ Allows HTTP traffic from the internal VPC CIDR only.

**🧠 Pro Tip: Always start with a “deny all” base policy, then add explicit allow rules — similar to Zero Trust network principles.**







# 🧠 Kubernetes Image Scanning
## 🚨 Why Image Scanning?
Container images often include:
  - Vulnerable libraries (known CVEs)
  - Misconfigurations (e.g., running as root)
  - Secrets accidentally left inside the image

Performing image scanning helps identify these issues before they reach production, thus reducing the cluster’s attack surface.

🔍 When to Perform Image Scanning
| **Stage**          | **Where It Happens**                   | **Example Tools**                                  | **Purpose**                  |
| ------------------ | -------------------------------------- | -------------------------------------------------- | ---------------------------- |
| **Build-time**     | In CI/CD pipeline after image build    | `Trivy`, `Grype`, `Anchore`                        | Catch vulnerabilities early  |
| **Pre-deployment** | Before pushing image to registry       | Admission controllers, `OPA Gatekeeper`, `Kyverno` | Block non-compliant images   |
| **Runtime**        | Inside cluster (on running containers) | `Falco`, `Sysdig`, `Aqua`                          | Detect live threats or drift |


🧪 Example: Using Trivy in CI/CD
```yaml
# .github/workflows/image-scan.yml
name: Image Scan with Trivy

on:
  push:
    branches: [ main ]

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repo
        uses: actions/checkout@v3

      - name: Build Docker image
        run: docker build -t myapp:latest .

      - name: Scan image with Trivy
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: 'myapp:latest'
          format: 'table'
          exit-code: '1'  # Fail if vulnerabilities found
          vuln-type: 'os,library'
```

🧱 Integrating Image Scanning in Kubernetes
- Admission controllers (e.g., OPA Gatekeeper or Kyverno) can block pods using vulnerable or unscanned images.
- Use ImagePolicyWebhook to enforce security policies dynamically.
- Combine with Notary or Cosign for signed and verified images.


# 🧩 Kubernetes Admission Controllers
## 🎯 What Are Admission Controllers?
Admission Controllers are plug-ins that intercept requests sent to the Kubernetes API server after authentication and authorization but before the object is persisted to etcd.
They act like “gatekeepers” — inspecting, modifying, or rejecting requests to ensure they meet cluster policies or security standards.


## ⚙️ Admission Control Flow
Here’s how a typical request flows:
```text
kubectl apply -f pod.yaml
   │
   ▼
[Authentication]  ✅ → [Authorization] ✅ → [Admission Controllers] ⚙️ → [etcd Persistence]
```

At the admission stage, controllers can:
- Validate the request (approve/reject)
- Mutate the request (add/modify fields automatically)

## 🧩 Common Built-in Admission Controllers
| Controller              | Type       | Description                                                  |
| ----------------------- | ---------- | ------------------------------------------------------------ |
| **NamespaceLifecycle**  | Validating | Prevents deletion of active namespaces                       |
| **LimitRanger**         | Validating | Enforces CPU/memory limits                                   |
| **ServiceAccount**      | Mutating   | Automatically assigns a ServiceAccount to Pods               |
| **DefaultStorageClass** | Mutating   | Assigns default StorageClass to PVCs                         |
| **NodeRestriction**     | Validating | Ensures kubelets can modify only their own Node objects      |
| **PodSecurity**         | Validating | Enforces Pod Security Standards (Baseline, Restricted, etc.) |


You can see which ones are enabled using:
```bash
kube-apiserver --help | grep enable-admission-plugins
```

# 🔐 Kubernetes Secrets Encryption
## 🧩 What Are Secrets?
Kubernetes Secrets are used to store sensitive data — things like passwords, tokens, SSH keys, and TLS certificates — in a base64-encoded format.
## 📦 Example:
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  username: YWRtaW4=
  password: c3VwZXJzZWNyZXQ=
```
⚠️ Base64 is not encryption, it’s just encoding — anyone who can read etcd can decode these values easily.
That’s why Kubernetes supports encryption at rest — i.e., encrypting secrets before they’re stored in etcd.

## 🧠 What Is Secrets Encryption?
Secrets Encryption ensures that:
  - Sensitive resources (Secrets, ConfigMaps, Tokens, etc.) are encrypted before being written to etcd.
  - Only the API Server can decrypt them, using the configured keys.
This protects against:
  - etcd data theft
  - Backup leaks
  - Disk-level attacks on control plane nodes

## ⚙️ How It Works
1. When you create or update a Secret, the API Server:
  - Uses an encryption provider (e.g., AES-CBC, aescbc, kms) defined in its config file.
  - Encrypts the Secret data.
  - Stores the encrypted blob in etcd.
2. When you read the Secret (e.g., kubectl get secret db-secret -o yaml):
  - The API Server decrypts it using the same key.
  - Sends the decrypted value in the response.
  - etcd itself never sees the plaintext secret — only ciphertext.

## 🧾 Enabling Encryption at Rest
### 1️⃣ Create the Encryption Configuration File
Usually located at `/etc/kubernetes/encryption-config.yaml`
```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      - aescbc:
          keys:
            - name: key1
              secret: ABase64EncodedSecretKeyHere123==
      - identity: {}
```
Explanation:
- aescbc: Algorithm used to encrypt secrets.
- keys: Contains one or more encryption keys (base64 encoded).
- identity: Means “no encryption” — used as a fallback.

### 2️⃣ Configure API Server to Use It
Add the following flag in /etc/kubernetes/manifests/kube-apiserver.yaml:
```bash
- --encryption-provider-config=/etc/kubernetes/encryption-config.yaml
```

Restart the API server for the change to take effect.
3️⃣ Verify Encryption
Create a secret:
```bash
kubectl create secret generic test-secret --from-literal=password=12345
```
Then check the raw data in etcd:
```bash
ETCDCTL_API=3 etcdctl get /registry/secrets/default/test-secret \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key | hexdump -C
```
➡️ You should see binary ciphertext, not base64 plain text.

## ✅ Best Practices
- Always enable encryption at rest for production clusters.
- Use KMS provider in cloud or on-prem HSM.
- Periodically rotate keys.
- Limit etcd access (only API server should connect).
- Backup encryption config securely — loss of keys = loss of secrets.
- Use RBAC to restrict who can view Secret objects.
