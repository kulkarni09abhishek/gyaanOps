# ⚙️ Kubernetes Scheduling — Manual Scheduling

---

## 🧠 What is Scheduling in Kubernetes?
In Kubernetes, **scheduling** is the process of assigning Pods to Nodes.  
By default, this is handled **automatically** by the **Kubernetes Scheduler**, which decides where a Pod should run based on:
- Available CPU / Memory
- Node taints and tolerations
- Affinity / Anti-Affinity rules
- Storage availability
- Node selectors and labels

However, Kubernetes also allows **manual scheduling**, where you — the human — decide **which node** a Pod should run on.

---

## 🧩 Manual Scheduling

### 🔍 1. Default Behavior

When you create a Pod normally, **no node is pre-assigned** to it.  
The YAML definition of a new Pod looks something like this:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
spec:
  containers:
  - name: nginx
    image: nginx
```
- Notice there’s no nodeName in the spec.
- The scheduler automatically picks a node and updates the Pod object with:
```yaml
nodeName: worker-node-1
```
- The scheduler bases this decision on resource availability, node health, taints/tolerations, and other constraints.


## 🧭 2. Assigning Node Explicitly
If you want to bypass the scheduler and assign a Pod to a specific node manually,
you can add the nodeName field in the Pod spec like this:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-manual
spec:
  nodeName: worker-node-1
  containers:
  - name: nginx
    image: nginx
```
Now:
- Kubernetes skips the scheduling phase entirely.
- The Pod is directly bound to the specified node.
- If specified Node lacks resources or volume requirements, Pod remains in Pending state.
Once a Pod is created and assigned to a node, nodeName becomes immutable.
If you need to reschedule it to another node — you must delete the Pod and create a new one.

## Pod Stuck in Pending State
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: busybox
spec:
  nodeName: fake-node
  containers:
  - name: busybox
    image: busybox
    command: ["sleep", "3600"]
```
```text
The specified node (fake-node) doesn’t exist or lacks required resources → Pod can’t be scheduled.
```


# 📘 Understanding Labels and Selectors
In Kubernetes, **labels** and **selectors** are fundamental concepts used to **organize**, **query**, and **manage** resources efficiently. They provide a flexible mechanism to group and identify Kubernetes objects (like Pods, Services, Deployments, etc.) based on key-value pairs.

---

## 🏷️ Labels

**Labels** are **key-value pairs** attached to Kubernetes objects (such as Pods, Nodes, Services, Deployments, etc.).  
They are intended to specify **identifying attributes** that are meaningful and relevant to users but do not directly imply semantics to the core system.

### ✅ Example of a Label
```yaml
metadata:
  labels:
    app: frontend
    env: production
    tier: web
```
### 🧠 Label Characteristics
- Labels must be unique within an object, but different objects can share the same label.
- Labels are not hierarchical.
- They are used to select and group resources dynamically.

## 🔍 Label Selectors
A selector is a query over labels that helps identify a set of Kubernetes objects.
They are commonly used by controllers (like ReplicaSets, Deployments) and Services to manage Pods.

There are two main types of label selectors:
1. Equality-Based Selectors
These allow filtering by exact label key/value matches.
Operators:
- =
- ==
- !=

```yaml
selector:
  matchLabels:
    app: frontend
    env: production
```
This matches all Pods with both labels:
```yaml
app=frontend AND env=production
```
Alternative example using command line:
```bash
kubectl get pods -l app=frontend
kubectl get pods -l 'env!=production'
```

2. Set-Based Selectors
These allow filtering based on label keys and whether their values belong (or not) to a set of values.
Operators:
- in
- notin
- exists (no value needed)
```yaml
selector:
  matchExpressions:
    - { key: app, operator: In, values: [frontend, backend] }
    - { key: env, operator: NotIn, values: [dev] }
```
This matches all resources where:
- app is either frontend or backend
- and env is not dev

## ⚙️ Example Use Cases
🧩 1. Service Selecting Pods
A Service uses label selectors to determine which Pods it should route traffic to.

🧩 2. Deployment Managing Pods
A Deployment uses label selectors to know which Pods it controls.

🧩 3. Filtering with kubectl
You can use label selectors directly in CLI commands for management and debugging.
```bash
# Get all pods with label app=frontend
kubectl get pods -l app=frontend

# Get pods in production environment
kubectl get pods -l env=production

# Delete all pods that are not in production
kubectl delete pods -l 'env!=production'
```

💡 Best Practices
- Use consistent label keys across your clusters (app, env, tier, version).
- Avoid encoding complex information in labels — keep them simple.
- Leverage selectors for automation, scaling, and CI/CD pipelines.
- Use annotations (not labels) for non-identifying metadata (e.g., build number, commit SHA).


# 🚧 Taints and Tolerations
**Taints** and **Tolerations** are key mechanisms in Kubernetes used to **control which Pods can be scheduled onto which Nodes**.  
They act as a **two-way control system** — Nodes **repel** certain Pods using *taints*, and Pods **accept or tolerate** those taints using *tolerations*.

This is essential for:
- Isolating workloads  
- Reserving nodes for special purposes  
- Preventing unwanted scheduling  
- Managing resource allocation and multi-tenancy

---

## 🧠 1. The Concept

Think of **taints** as a *“Keep Out”* sign placed on a Node, and **tolerations** as a *“Pass”* that allows specific Pods to enter despite that sign.

- **Taint (on Node):** “Only Pods that can tolerate me are allowed here.”
- **Toleration (on Pod):** “I can live with this Node’s condition.”

Kubernetes scheduler uses these to decide *where* a Pod can be placed.

---

## ⚙️ 2. How Taints Work

A **taint** is applied to a **Node** and has three parts:
```key=value:effect```

### 🔹 Example
```bash
kubectl taint nodes node1 dedicated=frontend:NoSchedule
```

## 🧩 3. Taint Effects
| Effect             | Description                                                                                                                            |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| `NoSchedule`       | New Pods **will not be scheduled** unless they tolerate the taint. Existing Pods remain unaffected.                                    |
| `PreferNoSchedule` | Scheduler will **try to avoid** placing Pods on the node, but it’s a soft preference (not guaranteed).                                 |
| `NoExecute`        | New Pods that don’t tolerate the taint **won’t be scheduled**, and existing Pods without toleration **will be evicted** from the node. |


## 🧩 4. Tolerations Explained
A toleration is defined in the Pod spec. It allows a Pod to be scheduled onto Nodes that have matching taints.
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: frontend-pod
spec:
  tolerations:
    - key: "dedicated"
      operator: "Equal"
      value: "frontend"
      effect: "NoSchedule"
  containers:
    - name: nginx
      image: nginx
```
This Pod tolerates the dedicated=frontend:NoSchedule taint,
so it can be scheduled on node1 from our earlier example.

## ⚙️ 5. Toleration Fields
| Field               | Description                                                                                | Example                       |
| ------------------- | ------------------------------------------------------------------------------------------ | ----------------------------- |
| `key`               | The taint key the toleration matches.                                                      | `"dedicated"`                 |
| `operator`          | How the key/value comparison is done. Default: `Equal`.                                    | `"Equal"`, `"Exists"`         |
| `value`             | The taint value to match (if using `Equal`).                                               | `"frontend"`                  |
| `effect`            | The taint effect to match. Optional.                                                       | `"NoSchedule"`, `"NoExecute"` |
| `tolerationSeconds` | Used only with `NoExecute` taints — defines how long a Pod will stay before being evicted. | `3600` (1 hour)               |


### 🧩 Operator Types
Equal (default) — Matches a taint with the same key and value.
```yaml
- key: "dedicated"
  operator: "Equal"
  value: "frontend"
  effect: "NoSchedule"
```
→ Matches dedicated=frontend:NoSchedule

Exists — Matches a taint with the given key, regardless of value.
```yaml
- key: "dedicated"
  operator: "Exists"
  effect: "NoSchedule"
```
→ Matches any taint with key dedicated and effect NoSchedule.

## 🧾 8. Common Commands
| Command                                       | Description                  |
| --------------------------------------------- | ---------------------------- |
| `kubectl taint nodes <node> key=value:effect` | Add a taint                  |
| `kubectl taint nodes <node> key:effect-`      | Remove a taint               |
| `kubectl describe node <node>`                | View taints on a node        |
| `kubectl get pods -o wide`                    | See where Pods are scheduled |



# 🧭 Node Affinity and Pod Affinity / Anti-Affinity in Kubernetes
Kubernetes provides **affinity** and **anti-affinity** rules to influence **how Pods are scheduled** on Nodes and with respect to **other Pods**.  
These rules let you **control placement** for performance, reliability, or data locality — without hardcoding specific Nodes.

---

## 🧩 1. Overview

| Type | Applies To | Purpose |
|------|-------------|----------|
| **Node Affinity** | Nodes | Schedule Pods *on specific Nodes* based on labels |
| **Pod Affinity** | Other Pods | Schedule Pods *together* (co-locate) |
| **Pod Anti-Affinity** | Other Pods | Schedule Pods *apart* (avoid same Node/zone/etc.) |

---

## 🧱 2. Node Affinity

**Node Affinity** lets you tell the scheduler **which Nodes a Pod prefers or requires**.  
It works **similar to nodeSelector**, but is much more expressive and flexible.

### 🎯 Key Idea:
> “I want my Pod to run *on* Nodes with certain labels.”

---

### 🧠 Node Labels Recap

Nodes can have labels like:
```bash
kubectl label node node1 disktype=ssd
kubectl label node node2 zone=us-east1-a
```
You can view them using:
```bash
kubectl get nodes --show-labels
```

### 🧩 Node Affinity Example
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: node-affinity-demo
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: disktype
                operator: In
                values:
                  - ssd
  containers:
    - name: nginx
      image: nginx
```

Explanation:
- requiredDuringSchedulingIgnoredDuringExecution → This is a hard requirement.
- Pod will only be scheduled on Nodes where disktype=ssd.
- If no Node matches, the Pod stays in Pending state.

### 🧮 Node Affinity Operators
| Operator       | Meaning                                                |
| -------------- | ------------------------------------------------------ |
| `In`           | Key’s value is in the provided list                    |
| `NotIn`        | Key’s value is not in the list                         |
| `Exists`       | Key exists (regardless of value)                       |
| `DoesNotExist` | Key does not exist                                     |
| `Gt` / `Lt`    | Key’s value (integer) greater or less than given value |


### 🧩 Preferred (Soft) Node Affinity
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: soft-affinity-demo
spec:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80
          preference:
            matchExpressions:
              - key: zone
                operator: In
                values:
                  - us-east1-a
  containers:
    - name: nginx
      image: nginx
```
Explanation:
- `preferredDuringSchedulingIgnoredDuringExecution` → Soft preference.
- Scheduler will try to place Pod in zone=us-east1-a, but if none are available, it will still schedule elsewhere.
👉 Tip: You can combine both required and preferred affinity rules for balanced control.

Note: "IgnoredDuringExecution" means that once a Pod is running, if Node labels change, it **won’t be evicted**.


## 🤝 3. Pod Affinity
Pod Affinity allows scheduling Pods close to other Pods — on the same Node, zone, region, etc.
This is useful for:
- Improving communication between Pods (low latency)
- Keeping related microservices together

🎯 Key Idea:
“I want to run with Pods that have specific labels.”

🧩 Pod Affinity Example
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-affinity-demo
  labels:
    app: frontend
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchExpressions:
              - key: app
                operator: In
                values:
                  - backend
          topologyKey: "kubernetes.io/hostname"
  containers:
    - name: nginx
      image: nginx
```
Explanation:
- The Pod will only schedule onto a Node that already runs a Pod with label app=backend.
- topologyKey: kubernetes.io/hostname → ensures affinity at Node level (same Node).

## 🚫 4. Pod Anti-Affinity
Pod Anti-Affinity prevents Pods from being placed together.
It’s used for high availability, load distribution, or fault tolerance.

🎯 Key Idea:
“I want to run away from Pods that have specific labels.”

### 🧩 Pod Anti-Affinity Example
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchExpressions:
                  - key: app
                    operator: In
                    values:
                      - web
              topologyKey: "kubernetes.io/hostname"
      containers:
        - name: nginx
          image: nginx
```
Explanation:
- Ensures no two Pods with label app=web are scheduled on the same Node.
- Increases resilience: one node failure doesn’t kill all replicas.


## ⚙️ 5. Combining Rules
You can mix Node Affinity, Pod Affinity, and Anti-Affinity together for powerful scheduling logic.

### 🧩 Example: Real-World Scenario
```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: node-type
              operator: In
              values: ["high-memory"]
  podAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 50
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app: cache
          topologyKey: "kubernetes.io/hostname"
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: web
        topologyKey: "topology.kubernetes.io/zone"
```
Meaning:
- Must run on node-type=high-memory
- Prefer to be on the same Node as Pods labeled app=cache
- Must not be on the same zone as Pods labeled app=web

💡 Best Practices
- Use Node Affinity for infrastructure constraints (e.g., GPUs, SSDs, regions, zones)
- Use Pod Affinity for co-located components (e.g., frontend with backend for low latency)
- Use Pod Anti-Affinity for redundancy (e.g., replicas of the same service on different nodes)
- Always define topology keys clearly — defaulting to hostname may cause unintended tight packing.
- Balance between hard (required) and soft (preferred) rules to avoid Pods being stuck in the Pending state.


# 🧭 Understanding `nodeSelector`
In Kubernetes, **`nodeSelector`** is the **simplest and most direct way** to tell the scheduler **which Nodes a Pod should run on**.  
It allows you to **match Pods to Nodes** based on **Node labels** — effectively controlling Pod placement in a straightforward way.

---

## 🧱 1. What Is `nodeSelector`?

Every Node in Kubernetes can be **labeled** with key-value pairs, such as:

```bash
kubectl label node node1 disktype=ssd
kubectl label node node2 region=us-east1
```
These labels describe the Node’s attributes (like hardware, location, or purpose).
Then, a Pod can use nodeSelector to request placement only on Nodes that match certain labels.

🎯 Concept:
“Schedule this Pod only on Nodes that have these labels.”


## 🧩 2. Basic Example
🔹 Step 1: Label a Node
```bash
kubectl label node worker-1 disktype=ssd
```

🔹 Step 2: Create a Pod with nodeSelector
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: node-selector-demo
spec:
  nodeSelector:
    disktype: ssd
  containers:
    - name: nginx
      image: nginx
```
➡️ The Pod will run only on a Node where disktype=ssd.
If no matching Node exists, the Pod will stay in Pending state.


⚙️ 3. How It Works
The scheduler looks for Nodes whose labels match the nodeSelector key-value pairs.
It picks one of the matching Nodes that also meets:
  - Resource requirements (CPU, memory)
  - Other scheduling constraints (taints, tolerations, etc.)
  - The Pod is bound to that Node.

## 🧩 4. Multiple Label Matching
You can specify multiple key-value pairs, and all must match for scheduling to succeed.
```yaml
spec:
  nodeSelector:
    disktype: ssd
    region: us-east1
```
➡️ The Pod will only be scheduled on Nodes that have both:
- disktype=ssd
- region=us-east1


# ⚙️ Resource Quota, LimitRange, Requests, and Limits

- **Resource Requests and Limits** (per Pod/container)
- **LimitRange** (per namespace defaults and constraints)
- **ResourceQuota** (per namespace total usage limits)

These work together to prevent any single application or team from monopolizing cluster resources.

--- 

## 🧠 Resource Requests and limits

> **Request = Minimum guaranteed amount of resource.**
- The Kubernetes **scheduler** uses requests to decide which Node can fit the Pod.
- If a Node doesn’t have enough **available requested** CPU/memory, the Pod won’t schedule there.
- The container is **guaranteed** at least this much resource when running.

> **Limit = The upper cap of resources a container can consume.**
- The container cannot exceed this amount of resource.
- If it tries:
  - **CPU:** The container is throttled (not killed).
  - **Memory:** The container is killed (OOMKilled) and may be restarted.

### 🧩 Example: Pod with Requests and Limits
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: resource-demo
spec:
  containers:
    - name: app
      image: nginx
      resources:
        requests:
          memory: "256Mi"
          cpu: "500m"
        limits:
          memory: "512Mi"
          cpu: "1"
```
Explanation:
Requests:
  - 256MiB of memory
  - 0.5 CPU core
→ Scheduler ensures the Node can provide at least this much.

Limits:
  - 512MiB of memory
  - 1 CPU core
→ Container cannot exceed these values at runtime.


## 📦 2. LimitRange (Namespace-Level Constraints)
A LimitRange is applied within a namespace to:
  - Set default resource requests and limits.
  - Define minimum and maximum allowed values.
This ensures that every Pod in a namespace behaves within consistent resource boundaries.
```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: app-limits
  namespace: dev
spec:
  limits:
    - type: Container
      max:
        cpu: "2"
        memory: "2Gi"
      min:
        cpu: "100m"
        memory: "128Mi"
      default:
        cpu: "500m"
        memory: "512Mi"
      defaultRequest:
        cpu: "200m"
        memory: "256Mi"
```
🧠 Behavior
- If a Pod doesn’t define requests or limits → the default values are applied automatically.
- If a Pod tries to request or limit outside the allowed range → creation fails.



## 🧱 3. ResourceQuota (Namespace-Level Usage Control)
A ResourceQuota enforces total resource usage limits for a namespace.
It’s a way for cluster administrators to control how much total CPU, memory, storage, and number of objects (Pods, Services, PVCs, etc.) a team can consume.
```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-quota
  namespace: dev
spec:
  hard:
    requests.cpu: "2"
    requests.memory: "2Gi"
    limits.cpu: "4"
    limits.memory: "4Gi"
    pods: "10"
    persistentvolumeclaims: "5"
```

🔁 How They Work Together
- LimitRange enforces what individual containers can request in the namespace.
- ResourceQuota caps the total usage of all containers in the namespace.
- Requests & Limits define each container’s actual usage contract.

## 🔍 4. Viewing and Monitoring Resources
View Namespace Quotas
```bash
kubectl get resourcequota -n dev
kubectl describe resourcequota dev-quota -n dev
```

View Namespace LimitRanges
```bash
kubectl get limitrange -n dev
kubectl describe limitrange app-limits -n dev
```

View Resource Usage per Pod
```bash
kubectl top pod -n dev
```


# ⚓ Static Pods in Kubernetes
**Static Pods** are a special type of Pod that is **managed directly by the kubelet** on a specific Node — **not by the API server** or a controller like the Deployment or ReplicaSet.  
They are often used for **core system components** (e.g., `kube-apiserver`, `kube-scheduler`, etc.) or **special-purpose workloads** that must always run on specific Nodes (like monitoring agents or storage daemons).

---

## 🧩 1. What Are Static Pods?

Normally, Kubernetes Pods are created and managed by the **control plane** — specifically the **API server** and **scheduler**.  
However, **static Pods** bypass this and are **started directly by the kubelet**.

> 📌 **Definition:**  
> A **Static Pod** is a Pod that is **defined by a file** on a Node’s filesystem.  
> The **kubelet watches that file** and ensures the Pod is always running — even if the control plane is down.

---

## 🧱 2. Why Use Static Pods?

| Use Case | Description |
|-----------|-------------|
| **Bootstrapping the control plane** | When setting up Kubernetes manually (kubeadm, etc.), static Pods are used to start `etcd`, `kube-apiserver`, `kube-controller-manager`, and `kube-scheduler`. |
| **High reliability** | They run even if the control plane or API server is unavailable. |
| **Node-specific workloads** | You can pin workloads to specific Nodes permanently (e.g., local monitoring or logging agents). |

---

## ⚙️ 3. How Static Pods Work

### 🧠 Core Concept

- The **kubelet** on each Node has a configuration field called `--pod-manifest-path` or `--manifest-url`.
- The kubelet **watches** this directory (or URL) for YAML manifests.
- For each file in that path, the kubelet:
  - Creates a Pod directly on the Node.
  - Keeps it running (restart on failure).
  - Automatically recreates it if the file changes.

> These Pods **don’t go through the scheduler** — they are bound directly to the Node where the kubelet runs.

---

### 🧩 Example: Static Pod Manifest
Let’s say we define a static Pod manifest on a Node at: `/etc/kubernetes/manifests/static-nginx.yaml`
```yaml

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: static-nginx
  namespace: default
spec:
  containers:
    - name: nginx
      image: nginx
      ports:
        - containerPort: 80
```
The kubelet running on that Node will automatically:
- Detect the file.
- Start the Pod.
- Keep it running as long as the file exists.

## 🧮 4. How Kubelet Manages Static Pods
Pod Lifecycle
- When kubelet finds the manifest file, it creates and runs the Pod.
- If the file is deleted, the Pod is stopped and removed.
- If the file is updated, kubelet recreates the Pod with new specs.

Pod Name
The kubelet automatically adds a suffix to the Pod’s name to indicate its Node origin:
<pod-name>-<node-name>

Example:
static-nginx-worker1

Mirror Pods
- Kubelet creates a “mirror Pod” object in the Kubernetes API server.
- This mirror Pod is read-only — it lets you see static Pods with commands like:
```bash
kubectl get pods -A
```
But you cannot edit or delete it via kubectl.
(You must modify or delete the local manifest file instead.)


# ⚔️ Static Pods vs DaemonSets 
Both **Static Pods** and **DaemonSets** ensure that certain Pods run on specific Nodes — but they do so in **very different ways** and are used for **different purposes**.

---

## 🧩 1. Overview

| Concept | Description |
|----------|-------------|
| **Static Pods** | Pods managed **directly by the kubelet** using local manifest files on each Node. |
| **DaemonSets** | A **Kubernetes controller** that automatically ensures one (or more) Pods run on **every** or **selected** Node, managed via the API server. |

---

## 🧱 2. Key Difference in Management

| Feature | **Static Pods** | **DaemonSets** |
|----------|------------------|----------------|
| **Managed by** | `kubelet` (local to Node) | `kube-controller-manager` (via API server) |
| **Pod definition stored** | On each Node’s filesystem (e.g., `/etc/kubernetes/manifests`) | In the Kubernetes API (via `kubectl apply`) |
| **Scheduling** | Manual — always tied to that Node | Automatic — controller schedules Pods on selected Nodes |
| **Visibility in API** | Shown as *mirror Pods* (read-only) | Fully visible and manageable via API |
| **Self-healing** | Kubelet restarts it locally if it fails | DaemonSet controller recreates Pods as needed |
| **Updates** | Edit YAML file on each Node | `kubectl apply` to DaemonSet — controller rolls out changes |
| **Portability** | Node-specific | Cluster-wide, portable definition |
| **Common use case** | Cluster bootstrap and system components | Cluster-wide agents, log collectors, monitoring, etc. |

**Note: Both bypass the kube-scheduler.**


# 🩺 Kubernetes Probes — Liveness, Readiness & Startup
---

## 💡 What Are Probes?

In Kubernetes, **probes** are **health checks** performed by the **Kubelet** on your containers.

They help Kubernetes determine:
- Whether a container is **alive** and should keep running  
- Whether it is **ready** to accept traffic  
- Whether it has **successfully started**

> 📘 Think of probes as “health sensors” for your Pods — they tell Kubernetes when to restart, wait, or route traffic.

---

## ⚙️ Types of Probes

Kubernetes defines **three** types of probes:

| Probe Type | Purpose | Action on Failure |
|-------------|----------|-------------------|
| **Liveness Probe** | Checks if the container is alive (healthy). | Container is **restarted**. |
| **Readiness Probe** | Checks if the app is ready to receive traffic. | Pod is **removed from Service endpoints** (no traffic). |
| **Startup Probe** | Checks if the app has successfully started. | If it fails, the container is **killed and restarted**. Prevents early liveness failures. |

---

## 🔬 Probe Mechanisms

Each probe can check container health in **three ways**:

| Probe Type | Description | Example |
|-------------|--------------|----------|
| **HTTP probe** | Sends an HTTP request to a specified endpoint. | `/healthz` |
| **TCP probe** | Opens a TCP socket on a port. | Port `8080` |
| **Exec probe** | Runs a command inside the container. | `cat /tmp/healthy` |

---

## 🧩 Example: Liveness Probe (HTTP)

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: liveness-http
spec:
  containers:
  - name: myapp
    image: nginx
    livenessProbe:
      httpGet:
        path: /healthz
        port: 80
      initialDelaySeconds: 5
      periodSeconds: 10
```
📘 Explanation:
- Kubernetes waits 5 seconds after the container starts.
- Then it hits http://<pod-ip>:80/healthz every 10 seconds.
- If the endpoint doesn’t return 2xx or 3xx, the container is restarted.

## 🧠 Example: Readiness Probe (TCP)
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: readiness-tcp
spec:
  containers:
  - name: mydb
    image: postgres
    readinessProbe:
      tcpSocket:
        port: 5432
      initialDelaySeconds: 10
      periodSeconds: 5
```

📘 Explanation:
- Checks if port 5432 is open (Postgres ready).
- If not ready, the Pod won’t receive traffic from the Service.
- Once the port responds, the Pod becomes part of the load-balanced endpoints.

## 🧱 Example: Exec Probe
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: liveness-exec
spec:
  containers:
  - name: test-container
    image: busybox
    args:
    - /bin/sh
    - -c
    - touch /tmp/healthy; sleep 30; rm -f /tmp/healthy; sleep 600
    livenessProbe:
      exec:
        command: ["cat", "/tmp/healthy"]
      initialDelaySeconds: 5
      periodSeconds: 5
```

📘 Explanation:
- As long as /tmp/healthy exists, the probe passes.
- After 30s, the file is deleted → probe fails → container restarts.

## 🚀 Example: Startup Probe (for slow apps)
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: startup-probe
spec:
  containers:
  - name: slow-app
    image: myapp:latest
    startupProbe:
      httpGet:
        path: /healthz
        port: 8080
      failureThreshold: 30
      periodSeconds: 10
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      periodSeconds: 10
```

📘 Explanation:
- startupProbe gives the app up to 30 × 10 = 300s (5 minutes) to start.
- Only after success does Kubernetes start checking the livenessProbe.
- Prevents premature restarts for apps with slow boot times.

## Summary
| Probe Type    | Purpose                            | Action                 | Example Use             |
| ------------- | ---------------------------------- | ---------------------- | ----------------------- |
| **Liveness**  | Checks if container is alive       | Restart container      | Fix stuck processes     |
| **Readiness** | Checks if app is ready for traffic | Remove from Service    | Wait until DB connected |
| **Startup**   | Checks if app started properly     | Prevent false restarts | Slow startups           |


## 🧩 How Kubernetes Handles Multiple Probes on the Same Container
In Kubernetes, **a single container can have all three probes** —  
👉 `livenessProbe`, `readinessProbe`, and `startupProbe` — configured together.  
But they don’t all run at once.  
Kubernetes has a **defined order and priority** for how it ev

### ⚙️ Probe Execution Flow
- If a `startupProbe` **exists**, it runs **first and exclusively**.
- During this time:
  - **`livenessProbe` and `readinessProbe` are disabled**.
  - Kubernetes only checks the `startupProbe` results.
- Only when the `startupProbe` **succeeds**, the other probes are activated.
- Once the startupProbe passes (or if none is defined): `livenessProbe` and `readinessProbe` start together
  - Both livenessProbe and readinessProbe run independently and continuously.
  - Their results affect the Pod differently
  - They do not block each other — they can succeed or fail independently.



# 🧩 Init Containers in Kubernetes
## 🧠 What are Init Containers?
In Kubernetes, Init Containers are special containers that run before the main application containers in a Pod start.
They are used to perform initialization tasks such as setup, configuration, dependency checks, or environment preparation that must be completed before the main application starts.
Key differences from regular containers:
  - Init containers always run to completion before the main containers start.
  - They run sequentially — each one must finish successfully before the next begins.
  - If an init container fails, Kubernetes restarts the Pod (based on its restart policy).
  - Once all init containers complete successfully, Kubernetes starts the main application containers.

## ⚙️ Why Init Containers?
Common use cases include:
- ✅ Dependency checks: Wait for a database or service to be available.
- 🧩 Configuration setup: Generate or modify config files before starting the main container.
- 🧱 Database migrations: Perform schema migrations or pre-checks before running the app.
- 🔐 Security tasks: Validate secrets or perform vulnerability scans before launching.
- 📦 Preloading data: Download dependencies or cache data before main app execution.

## 🧰 Example: Init Container Waiting for Database
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-init
spec:
  initContainers:
    - name: wait-for-db
      image: busybox
      command: ['sh', '-c', 'until nc -z my-database 3306; do echo waiting for db; sleep 3; done;']
  containers:
    - name: main-app
      image: nginx
      ports:
        - containerPort: 80
```

Explanation:
- The init container (wait-for-db) runs first.
- It checks whether the database (my-database:3306) is reachable.
- Once successful, it exits, and only then the main nginx container starts.

🧩 Example: Using Init Containers for Configuration
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: init-config-example
spec:
  volumes:
    - name: config-volume
      emptyDir: {}
  initContainers:
    - name: create-config
      image: busybox
      command:
        - sh
        - -c
        - echo "app.message=Hello from Init Container" > /config/app.properties
      volumeMounts:
        - name: config-volume
          mountPath: /config
  containers:
    - name: main-app
      image: busybox
      command: ['sh', '-c', 'cat /config/app.properties && sleep 3600']
      volumeMounts:
        - name: config-volume
          mountPath: /config
```

Explanation:
- The init container creates a config file inside the shared emptyDir volume.
- The main container reads that config when it starts.

## 🧠 Key Points to Remember
| Feature              | Description                                                                               |
| -------------------- | ----------------------------------------------------------------------------------------- |
| **Execution Order**  | Sequential; each must succeed before the next starts                                      |
| **Failure Handling** | Pod restarts until init container succeeds                                                |
| **Lifecycle**        | Init containers run once per Pod startup                                                  |
| **Shared Volumes**   | Useful for passing files/configs to main containers                                       |
| **Logs**             | Each init container has its own logs (view with `kubectl logs <pod> -c <init-container>`) |
